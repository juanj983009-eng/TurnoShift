## 3. Dos objetivos relacionados, pero diferentes

### 3.1. Objetivo académico

Demostrar que el equipo puede:

- Formular un problema.
    
- Delimitar una solución.
    
- Definir requisitos.
    
- Diseñar arquitectura y datos.
    
- Implementar funcionalidades.
    
- Verificarlas.
    
- Explicar decisiones y limitaciones.
    
- Presentar evidencias del proceso.
    

La evaluación concreta depende de lo que indique el curso.

### 3.2. Objetivo del producto

Construir un MVP que pueda utilizarse en un piloto y evolucionar hacia una operación comercial sostenible.

Esto requiere aspectos que podrían superar lo exigido para la calificación:

- Aislamiento entre empresas.
    
- Recuperación operativa.
    
- Soporte.
    
- Validación con usuarios.
    
- Disposición a pagar.
    
- Renovación.
    

### 3.3. Regla de separación

- Aprobar el curso no demuestra viabilidad comercial.
    
- Tener interés comercial no reemplaza los entregables académicos.
    
- Una demostración funcional no acredita preparación para producción.
    
- Terminar documentos no equivale a implementar el sistema.
    

Los resultados se presentan por separado.

Antes de desarrollar o presentar avances formales, se debe acordar una versión de referencia con:

### 7.1. Exclusiones que deben permanecer visibles

El MVP no incorpora:

- Asistencia.
    
- Nómina.
    
- Biometría o GPS.
    
- Planificación automática.
    
- Aplicación móvil nativa.
    
- Operación multisede.
    
- Cobros automáticos.
    

Si el curso exige alguna capacidad diferente, se registra la incompatibilidad y se decide cómo resolverla.

No se cambia silenciosamente el producto para aparentar que siempre tuvo otro alcance.

### 7.2. Si la rúbrica obliga a ajustar

Opciones:

- Aclarar cómo el alcance actual satisface el criterio.
    
- Ajustar la presentación o evidencia.
    
- Solicitar validación de una alternativa.
    
- Modificar alcance explícitamente.
    
- Revisar la viabilidad del proyecto para ese requisito.
    

La solución se documenta antes de construir trabajo adicional.

## 10. EDT y backlog

### 10.1. Funciones diferentes

- La **EDT** organiza el trabajo por entregables.
    
- El **backlog** organiza elementos implementables y priorizados.
    
- El **cronograma** sitúa trabajo y dependencias en el tiempo.
    

Deben corresponderse, pero no necesitan ser copias idénticas.

### 10.2. Estructura de EDT propuesta

1. Gestión y formulación.
    
2. Requisitos y procesos.
    
3. Diseño técnico y de interfaz.
    
4. Construcción.
    
5. Pruebas y correcciones.
    
6. Preparación operativa.
    
7. Documentación.
    
8. Sustentación y entrega.
    

La construcción se descompone usando las épicas e historias del documento 11.

### 10.3. Reglas

- Cada paquete tiene un resultado verificable.
    
- Incluye revisión y pruebas.
    
- No duplica trabajo de otro paquete.
    
- Tiene responsable.
    
- Sus criterios de término son claros.
    

“Programar sistema” no constituye una descomposición suficiente.

- Implementado.
    
- Probado.
    
- Observado en piloto.

> Se propone evaluar la disposición a pagar mediante un piloto.

No convertirlo en:

> El sistema demostró viabilidad comercial.

- Un objetivo.
    
- Una actividad ejecutada.
    
- Un resultado.
    
- Una limitación, cuando corresponda.

### 15.3. Guion propuesto

|   |   |   |
|---|---|---|
|Paso|Acción|Qué demuestra|
|1|Presentar problema y alcance|Comprensión del caso|
|2|Acceder como responsable|Sesión y rol|
|3|Mostrar equipo y políticas|Configuración|
|4|Crear o abrir borrador|Planificación|
|5|Mostrar un conflicto|Validación|
|6|Corregir y publicar|Publicación oficial|
|7|Consultar como colaborador|Acceso personal|
|8|Proponer intercambio|Flujo del solicitante|

|10|Aprobar como responsable independiente|Cambio atómico|
|11|Mostrar horario y reporte|Resultado|
|12|Mostrar historial y pruebas|Trazabilidad|

El guion se ajustará a la duración disponible.

### 15.4. Control del tiempo

Propuesta para un espacio breve:

- Problema y alcance: 2 minutos.
    
- Diseño y decisiones: 2 minutos.
    
- Recorrido funcional: 6 minutos.
    
- Pruebas, limitaciones y cierre: 2 minutos.
    

Los doce minutos son una referencia de ensayo, no una duración atribuida al curso.

Si el tiempo es menor, se reduce el recorrido y se identifican las evidencias complementarias.

### 15.5. Casos preparados

Se puede precargar un escenario para ahorrar tiempo, siempre que se explique.

No se presenta como creado en vivo algo que ya estaba preparado.

Las sesiones de distintos roles deben estar separadas para evitar confusión. No se añade un selector público para simular roles.
